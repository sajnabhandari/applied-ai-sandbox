## Plan from chat

Feature: Starred notes filter

Design from chat:

1. Data model changes
- Add `starred: false` field to each note dict
- Existing notes default to False if field missing

2. Backend changes
- Add toggle endpoint or action to flip `starred` boolean
- Add filtering logic for "starred only" view

3. UI changes
- Add star icon next to each note (click to toggle)
- Add filter option "Starred" in filter bar
- Highlight starred notes visually (optional styling)

4. Edge cases
- Existing notes without `starred` field must not break (treat as False)
- Multiple toggles should be idempotent
- Filtering should work when no notes are starred (empty list state)

5. Implementation plan (no code)
- Step 1: extend note model with `starred`
- Step 2: implement toggle logic
- Step 3: implement filtering logic
- Step 4: update UI rendering
- Step 5: test existing + new behavior

## Chat review

One piece of feedback I acted on:
- **Bug: `loop.index0` is wrong in filtered view.** The template used `loop.index0` as the URL index for the toggle route, but in the starred-only filter that's the index within the filtered list — not the real position in `app.notes`. Toggling note 0 in a filtered view of 2 starred notes would hit `app.notes[0]`, which is the wrong note. Fixed by passing `(original_index, note)` tuples from the view so the form always submits the real index.

## Workflow retro

This feature was built using a four-lane workflow: chat for planning, Claude Code for implementation, Copilot for small edits, and chat again for review. Each tool had a distinct role and removing any one of them would have made the process slower or less reliable.

Chat was most useful at the start for shaping the design of the feature (starred notes and filtering). It helped clarify data model changes, UI requirements, and edge cases before any code was written. Claude Code then executed the plan efficiently, handling the core implementation like adding the `starred` field and filter logic.

Copilot was only useful for small polish work such as renaming variables and adding docstrings. These were low-effort improvements that didn't require full agent reasoning. Chat again was valuable in review mode, where it caught issues like missing default handling for `starred` in older notes and helped surface edge cases I initially didn't consider.

If I re-did this workflow, I would tighten the initial chat design further by explicitly defining filtering behavior (especially default states) before implementation. That would reduce minor corrections during coding.

The most time was spent during review and debugging rather than planning or implementation. That felt correct, since correctness risks are best caught after code exists. Overall, the conductor model worked well: each tool was used where its strengths were highest, and my role was routing between them rather than doing all the work myself.
